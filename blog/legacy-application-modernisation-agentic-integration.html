Legacy Application Modernisation Through Agentic Integration

Your Core System Is Twenty Years Old and Has No API. AI Agents Can Still Work with It.

GJ
By Gangadevi JeyarajSenior Agentic AI Engineer · CPO, Enthiram.ai · 15 years in AI
23 November 2026 · 7 min read

The short answer

You do not need to rewrite a legacy system before AI agents can use it. Wrap each legacy capability as a governed tool, using the safest route available: an API, the database, files and queues, or the user interface as a last resort. Agents then run the process across old and new systems, and you replace legacy modules one at a time behind the same tool interface.

Key takeaways

  • Full rewrites are slow and risky. Wrapping delivers value in weeks and lowers the risk of the eventual replacement.
  • Choose the integration route in order: API, database, files and messages, then user interface.
  • The tool contract is the long-term asset. Agents depend on it, and the system behind it can change.
  • Legacy systems rarely protect against duplicates, so idempotency and verification have to be added in the tool layer.

Every large enterprise has one. A policy administration system from 2004. A mainframe ledger. A desktop application that only runs on one version of Windows and that three people fully understand. The business depends on it daily, and it has no API.

For years the options were two. Rewrite it, in a programme that takes four years and often stalls. Or put robotic process automation on top and accept scripts that break when a button moves. Agents give a third option that I have found more practical than either.

Why do big-bang rewrites fail?

The reasons are consistent.

  • The rules are not written down. They live in decades of code and in the heads of people close to retirement. The new system is specified from memory and misses cases.
  • The business keeps moving. By the time the replacement is ready, requirements have changed.
  • Value arrives at the end. Funding has to survive several budget cycles with nothing to show.
  • Cutover is all or nothing. One weekend carries the risk of the whole programme.

Meanwhile every AI initiative is told to wait until modernisation is complete. That wait now costs more than most teams admit.

What is agentic integration?

Agentic integration means making each legacy capability available as a well-defined tool, and letting agents run business processes across those tools.

An agent does not care that get_policy is served by a mainframe transaction and send_notification by a cloud service. It calls two tools. The legacy system becomes a participant in modern workflows without being changed.

This is the same idea I applied to end users when I built LegalAI at Pearl Media. Lawyers were not going to leave Microsoft Word, so we put the AI inside Word as an add-in. Legacy systems deserve the same respect. Meet them where they are.

Which integration route should you use?

I work down a ladder and stop at the first rung that meets the need. Each step down is more fragile, so it needs more protection.

Route Use when Main risk Protection
1. API The system or its vendor exposes one Rate limits, partial coverage Caching, clear timeouts
2. Database and change data capture You need to read, or to react to changes Bypassing business rules on write Read only. Never write directly to legacy tables
3. Files and message queues The system already imports and exports batches Delay, format drift Schema checks, reconciliation
4. User interface automation Nothing else exists Screens change, slow, brittle Verification after every action, human fallback

Reading through the database is usually safe and fast. Writing is different. Legacy applications enforce their rules in code, so a direct insert can create records the application considers impossible. For writes I go through whatever the application itself offers, even if that is the screen.

Interface automation has improved. Browser automation tools such as Playwright are stable for web front ends, and models that can operate a screen now handle desktop and terminal applications that scripts could not. I still treat it as the last resort and wrap it carefully.

What makes a legacy tool safe for an agent to call?

Legacy systems were built for careful human operators. They often lack the protections modern services have, so the tool layer has to supply them.

Identity. The tool runs with the entitlements of the person the agent is acting for. When I connected agents to internal systems through MCP servers at Enthiram.ai, each call was authenticated with OAuth2 and OIDC for this reason.

Idempotency. Many old systems will happily accept the same payment twice. The tool keeps its own record of request keys and refuses repeats.

Verification. After a write, the tool reads the record back and confirms the change before reporting success. With screen automation this is essential, because a click that appeared to work may not have saved.

Pace. A mainframe sized for two hundred clerks can be overwhelmed by an agent that works a thousand times faster. The tool enforces a queue and a rate limit.

Audit. Every call is logged with who, what, when and the result, so the agent's activity is as traceable as a clerk's.

Approval. Irreversible actions go to a person first.

How do you recover the knowledge trapped in the old system?

This is where language models help in a way that was not possible five years ago. They read old code well.

  1. Extract rules from code. A model reads COBOL, PL/SQL or stored procedures and drafts the business rule in plain language: "A policy lapses if the premium is unpaid 30 days after the due date, unless a grace flag is set."
  2. Review with experts. The people who know the system confirm or correct each rule. Their time goes into checking, not into writing from scratch.
  3. Record rules in the knowledge layer. They become part of the enterprise ontology, where agents and future developers can use them.
  4. Generate characterisation tests. Run real historical inputs through the old system and record the outputs. These tests define "current behaviour" and will check any replacement.

After this step the enterprise owns its rules in a form that survives the system that held them.

How does the legacy system finally get replaced?

Gradually, behind the tools, using the strangler fig approach.

Because agents depend on the tool contract and not on the system, you can rebuild one capability at a time. Rewrite address changes as a new service. Point update_address at it. Run old and new in parallel and compare results using the characterisation tests. When they match for long enough, retire that part of the legacy system. Agents and users notice nothing.

Each step is small and reversible, and value has been flowing since the first tool went live. The modernisation programme stops being a bet and becomes a sequence of safe changes.

What would I do in your first 30 days?

  • Week 1. Pick one process that is slowed by a legacy system. List the five capabilities it needs from that system.
  • Week 2. Wrap those five as tools, read-only first, by the safest route on the ladder.
  • Week 3. Add the write tools with idempotency, verification, rate limits and approval.
  • Week 4. Put an agent on the process with a person reviewing outcomes. Start rule extraction on the module you would most like to retire.

What changes in 2027?

Vendor support for widely used older platforms is running out. Mainstream maintenance for SAP ECC ends in 2027, for example. The engineers who know these systems are also leaving the workforce. Models that operate screens are also improving quickly, which will make the fourth rung of the ladder more dependable. I expect "wrap first, replace behind the interface" to become the standard route, with rewrites reserved for modules where the business case is clear. To run the resulting cross-system processes reliably, see long-running autonomous agent execution. For the data side, see unified enterprise data fabric.

Frequently asked questions

What is agentic integration for legacy systems?

It is an approach where each capability of a legacy application is exposed as a governed tool, and AI agents use those tools to run business processes across old and new systems without rewriting the legacy application first.

Can AI agents work with a system that has no API?

Yes. Agents can read through the database or change data capture, exchange files and messages, or operate the user interface through browser or screen automation. Each route needs controls such as verification, rate limits and audit.

How is agentic integration different from RPA?

RPA replays fixed scripts and breaks when screens or cases vary. Agentic integration wraps capabilities as tools with contracts, lets an agent handle variation and exceptions, and prefers APIs and data routes over screens.

What is the strangler fig pattern in modernisation?

It is a way of replacing a legacy system gradually. New services take over one capability at a time behind a stable interface, run in parallel with the old system until they match, and then the old part is retired.

Is it safe to let AI agents write to a legacy system?

It can be made safe by writing only through the application's own interfaces, adding idempotency keys and read-back verification in the tool layer, limiting the rate of calls, logging every action and requiring human approval for irreversible changes.
