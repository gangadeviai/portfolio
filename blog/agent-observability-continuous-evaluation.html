Agent Observability & Continuous Evaluation

If You Cannot See What Your AI Agent Did, You Cannot Trust It: Agent Observability and Continuous Evaluation

GJ
By Gangadevi JeyarajSenior Agentic AI Engineer · CPO, Enthiram.ai · 15 years in AI
23 November 2026 · 7 min read

The short answer

Trace every model call, tool call and handoff as one linked record per task. Evaluate in two places: before release, with a test suite that blocks a change if scores fall, and after release, by scoring a sample of real traffic every day. Feed production failures back into the test suite. This loop is what keeps an agent reliable as models, prompts and data change.

Key takeaways

  • Agents fail silently. They return a fluent answer and a 200 status while doing the wrong thing.
  • Evaluate the path the agent took, including each tool call, and the final output.
  • A release gate in CI is the single most valuable control. No passing score, no deploy.
  • Every production failure should become a permanent test case within a week.

Traditional software tells you when it is broken. A service throws an error, a status code turns red, a pager goes off. An agent that has gone wrong returns a confident, well-formatted answer. It chose the wrong tool, skipped a check, or quoted a policy that was replaced last month, and every dashboard stays green.

This is why I treat observability and evaluation as part of the agent, built at the same time as the first prompt. Teams that add them after an incident spend months earning back trust.

Why is monitoring agents different from monitoring software?

Four properties make the usual tools insufficient.

  • Non-determinism. The same input can produce different paths on different runs. One passing test proves little.
  • Multi-step paths. A final answer can look correct even though the agent took a forbidden shortcut to reach it.
  • Dependencies that change underneath you. A provider updates a model. A document is edited. Behaviour shifts with no deployment on your side.
  • Quality is a judgement. "Was this a good answer?" has no status code.

Uptime and latency still matter. They are simply no longer enough.

What should you trace?

Everything that contributes to a decision, linked under one trace ID for the task. I instrument with OpenTelemetry so the data is not locked to one vendor, and I record a span for each of these:

Span What I record
Model call Model and version, prompt template version, tokens in and out, latency, cost
Retrieval Query, sources returned, scores, the user's access scope
Tool call Tool name, arguments, result, duration, idempotency key
Policy gate Rule checked, decision, reason
Handoff From agent, to agent, task contract, acknowledgement
Human step Who approved or corrected, and what they changed

Personal data is redacted before a trace is stored. In the SOC 2 Type II agents I built at Enthiram.ai, this trail served two purposes: engineers used it to debug, and auditors used it as evidence that controls operated on every step.

One rule saves a lot of pain later. Version everything that can change behaviour: prompts, tools, model, retrieval configuration. When a metric moves, the first question is always "what changed?", and you want the trace to answer it.

How do you evaluate before release?

With a test suite that runs in CI and can block a deploy. I set this up with DeepEval and Braintrust in GitHub Actions, and it has stopped more bad changes than any review meeting.

Build the suite from real work. Start with 50 to 100 cases taken from actual tasks, including the awkward ones. For each, record the expected outcome and, where it matters, the expected path: which tools should be called and which must not be.

Score more than the final answer. I use three levels.

  • Outcome. Was the task completed correctly?
  • Trajectory. Were the right tools called with the right arguments, in a sensible order? Were any forbidden actions attempted?
  • Component. Was retrieval relevant? Is each claim supported by a source?

Run each case several times. Because of non-determinism I run important cases three to five times and look at the pass rate. A case that passes four times in five is a failing case.

Set thresholds and enforce them. If task success falls below the agreed line, or any safety case fails, the pipeline stops. The same gate applies to a model upgrade. A new model version is a code change as far as I am concerned.

How do you evaluate after release?

Offline tests cover what you imagined. Production shows you the rest. I score a sample of live traffic every day using two kinds of evaluators.

Deterministic checks are cheap and exact, so I run them on everything. Did the output match the schema? Was a citation present? Did the agent stay within its step budget? Did the gate block anything?

Model-based judges assess what rules cannot: is the answer grounded in the retrieved sources, did it address the question, was the tone right? A judge is itself a model and can be wrong. Before I trust one, I compare its scores with human labels on a few hundred examples and adjust its instructions until they agree closely. I recheck that agreement every quarter.

Human review still has a place. A small, steady sample reviewed by domain experts catches things no automated scorer will, and it produces the labels that keep the judges honest.

Which metrics belong on the dashboard?

I keep it to seven, and I show them to both engineering and the business owner.

  1. Task success rate. Completed correctly without human rescue.
  2. Tool-call accuracy. Correct tool, correct arguments.
  3. Policy adherence. Share of actions that passed the gate first time, and the count of blocked attempts.
  4. Groundedness. Share of answers fully supported by sources.
  5. Escalation rate. How often the agent hands over, and whether the handover was justified.
  6. Latency. Median and 95th percentile per task.
  7. Cost per completed task. Not cost per call. This is the number finance understands.

Alerts fire on movement, such as a five-point drop in task success over a day, and on any safety event.

How do you close the loop?

A production failure should not be fixed only in the prompt. It should become a test.

When a trace is marked as a failure, by a judge, a user or a reviewer, it is triaged within a few days. The input, the context and the correct outcome are added to the offline suite. From then on, every release proves that this failure cannot return. Over a year the suite becomes the most valuable asset the team owns, because it encodes everything the business has learned about what "correct" means.

What would I do in your first 30 days?

  • Week 1. Add tracing to one agent with a single trace ID per task. Start versioning prompts and tools.
  • Week 2. Build a first suite of 50 cases from real traces. Score outcome and trajectory.
  • Week 3. Wire the suite into CI as a release gate with agreed thresholds.
  • Week 4. Turn on daily scoring of sampled production traffic, calibrate one judge against human labels, and publish the seven-metric dashboard.

What changes in 2027?

Runs are getting longer and involve more agents, so evaluation has to cover a task that spans days and several vendors' systems. Tracing standards for generative AI are settling, which will make cross-vendor traces practical. Regulators are also asking for records of automated decisions, and a complete trace with rule checks is the natural form of that record. I expect "show me the trace" to become a routine audit request. For the long-run side see long-running autonomous agent execution, and for rule adherence over time see context rot and context engineering.

Frequently asked questions

What is agent observability?

Agent observability is the ability to see what an AI agent did and why. It is built on linked traces of every model call, retrieval, tool call, policy check and handoff for each task, together with metrics for quality, cost and latency.

What is continuous evaluation for AI agents?

It is the practice of evaluating an agent before every release with a test suite that can block deployment, and after release by scoring sampled production traffic every day. Failures found in production are added to the test suite.

How do you evaluate an AI agent, not only its final answer?

Score three levels: the outcome of the task, the trajectory of tool calls and decisions taken to reach it, and components such as retrieval relevance and groundedness. Run important cases several times because agents are non-deterministic.

Can an LLM be trusted to judge another LLM?

Only after calibration. Compare the judge's scores with human labels on a few hundred examples, refine its instructions until agreement is high, and recheck regularly. Use deterministic checks wherever a rule can decide.

Which metrics matter most for production agents?

Task success rate, tool-call accuracy, policy adherence, groundedness, escalation rate, latency at the 95th percentile and cost per completed task.
