Unified Enterprise Data Fabric

Your AI Agents Are Only as Good as the Data They Can Reach: Designing a Unified Enterprise Data Fabric

GJ
By Gangadevi JeyarajSenior Agentic AI Engineer · CPO, Enthiram.ai · 15 years in AI
20 November 2026 · 7 min read

The short answer

A unified enterprise data fabric is one governed way to find, trust and access data wherever it lives. For AI agents it means curated data products with owners and contracts, an active metadata catalogue, and tool-based access that carries the user's identity and permissions. Agents stop needing a custom integration for every system.

Key takeaways

  • Agent pilots stall on data access far more often than on model quality.
  • A fabric connects and governs data where it lives. It does not require copying everything into one database.
  • Agents should read data products through tools that enforce the user's permissions, never through shared service accounts.
  • Expose freshness and quality to the agent, so it can say "as of this morning" or decline to answer.

The first agent demo in most enterprises goes well. It runs on a clean extract someone prepared by hand. Then the team asks for production access to the ERP, the CRM, the document store and the data warehouse, and the project stops for three months. Security wants to know which data the agent will read. Nobody can answer, because the agent decides at run time.

I have seen more agent programmes delayed by this than by anything to do with models. The answer is a data fabric designed with agents as first-class consumers.

What is a data fabric, and what is it not?

A data fabric is an architecture that gives one consistent way to discover, govern and access data across many systems. The data can stay where it is. The fabric adds the metadata, the policies and the access layer that make it usable as a whole.

Three ideas get confused with each other, so here is how I separate them.

Concept Main idea Where it helps
Lakehouse One storage and compute platform for raw and curated data Refining data into trusted tables
Data mesh Domains own their data and publish it as products Accountability and scale across teams
Data fabric Unified metadata, governance and access across all of it Making data findable and safely usable

They are compatible. In practice I use a lakehouse for refinement, the product thinking from data mesh for ownership, and the fabric to tie it together.

Why do agents make this urgent?

A dashboard reads the same tables every day. A person approved those tables once. An agent chooses what to read while it works, combines sources nobody planned to combine, and may act on the result. Four problems follow.

  • Unknown access patterns. You cannot review every query in advance.
  • Shared credentials. Many early agents run on one powerful service account. Every user of the agent then sees everything the account can see.
  • Stale data treated as current. An agent does not know a table was last loaded on Friday unless something tells it.
  • Integration sprawl. Each new agent team builds its own connectors, and you end up maintaining forty of them.

How do I structure the data itself?

I use the medallion pattern, which I applied on Snowflake for an insurance claims platform.

  • Bronze holds data exactly as it arrived. It is the audit copy.
  • Silver is cleaned and conformed: types fixed, duplicates removed, identities matched.
  • Gold is shaped for the business: a claim with its policy, customer and payment history joined and ready.

Agents read from gold. That one rule removes a large class of errors, because the agent is never left to interpret raw operational tables. Documents follow the same path. They are parsed, split, classified and indexed, since most of what an enterprise knows is written in contracts, emails and notes.

What turns tables into something an agent can trust?

Three things, all metadata.

A catalogue with meaning. Each data product has a description, an owner and definitions that match the enterprise ontology. This is how an agent, or the engineer building it, finds the right source.

Lineage. When an agent states a number, you should be able to trace it to the gold table, the silver sources and the original system. In regulated work this is what turns an answer into evidence.

Quality and freshness signals. Every product publishes when it was last updated and whether its checks passed. I pass these to the agent with the data. An agent that knows the claims table is six hours old can say so. One that knows a quality check failed can decline and escalate.

How should agents get access?

Through tools, with the user's identity attached.

Each data product is exposed through a small set of functions, usually as an MCP server: get_claim, list_payments, search_policy_documents. The agent calls the function. The function applies the policy.

The important detail is whose permissions apply. When I connected agents to internal databases at Enthiram.ai, the MCP servers were secured with OAuth2 and OIDC so that each call carried the identity of the person the agent was working for. A regional manager's agent sees that region. The same agent, used by an auditor, sees more. No shared super-account exists to be misused.

Sensitive fields are handled before the model sees them. In the SOC 2 work I led, personal data was detected and redacted on the way into the prompt, and every read was written to an audit trail. Both controls live in the access layer, so each new agent inherits them.

What does a good data product contract contain?

I ask every domain team for the same short contract.

  1. Purpose and owner. What the product is for and who answers for it.
  2. Schema and definitions. Linked to ontology terms.
  3. Freshness target. For example, updated within 15 minutes.
  4. Quality checks. What is tested on each load.
  5. Access policy. Who can read which rows and columns.
  6. Change process. How consumers are warned before a breaking change.

Agents break quietly when a column is renamed. A contract with a change process is the cheapest protection I know.

What would I do in your first 30 days?

  • Week 1. Pick one agent use case and list every data source it needs. Note the owner and the access route for each.
  • Week 2. Build gold products for the top three sources, with contracts and freshness signals.
  • Week 3. Put an MCP server in front of them with identity pass-through and masking.
  • Week 4. Run the agent on the fabric, review the audit log with security, and use that review to approve the pattern for the next teams.

The goal of the first month is one approved path that every later agent can reuse.

What changes in 2027?

Agents will write as much as they read. Notes, decisions and extracted facts will flow back into the fabric, and that data needs the same contracts and quality checks as anything else. Data residency rules are also tightening, which means the fabric must know where each product physically lives and stop an agent from moving it across a border inside a prompt. Teams that have identity pass-through and a catalogue in place will handle both. Teams running on shared service accounts will be rebuilding.

For the meaning layer above the fabric, see enterprise ontology and semantic knowledge layer. For real-time data, see event-driven anomaly detection with Kafka.

Frequently asked questions

What is a unified enterprise data fabric?

It is an architecture that provides one governed way to discover, trust and access data across many systems. It combines a metadata catalogue, lineage, quality signals, policies and an access layer, while the data can remain in its source systems or a lakehouse.

What is the difference between a data fabric and a data mesh?

A data mesh is an operating model in which business domains own and publish data as products. A data fabric is the technical layer of unified metadata, governance and access. They work well together.

How should AI agents access enterprise data securely?

Agents should call governed tools, for example MCP servers, that enforce row and column policies using the identity of the user the agent is acting for. Shared service accounts and raw database connections should be avoided.

What is medallion architecture?

It is a way of refining data in three layers. Bronze keeps raw data as received, silver holds cleaned and conformed data, and gold holds business-ready data products. Agents should read from the gold layer.

Do I have to move all my data into one platform to build a data fabric?

No. A fabric connects and governs data where it lives. Many enterprises centralise the most used data in a lakehouse and reach the rest through federation or change data capture.
