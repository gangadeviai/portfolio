Context Rot & Context Engineering

Is Your Multi-Agent System Forgetting Its Own Rules? How I Fix Context Rot in Enterprise AI Agents

GJ
By Gangadevi JeyarajSenior Agentic AI Engineer · CPO, Enthiram.ai · 15 years in AI
23 November 2026 · 8 min read

The short answer

Context rot is the slow loss of the rules an AI agent was given as its run gets longer. It happens in four places: inside a long context window, during summarisation, in memory retrieval and at agent handoffs. You fix it by treating rules as protected data that the runtime re-injects, measures and enforces at the tool call, instead of trusting the model to remember a prompt.

Key takeaways

  • Context rot is an architecture problem. A bigger context window or a stricter prompt does not remove it.
  • Rules decay at four points: the window, compaction, retrieval and handoff. Each needs its own control.
  • The reliable control is a gate at the tool call that checks every action against the live rule set.
  • In my published tests, rule violations executed at tools fell from 60 to 79% down to zero.

Picture a claims pilot that runs cleanly for three weeks. The agents respect every approval limit. Then the pilot moves to cases that stay open for days, and a payment goes out above the limit that the first prompt stated in capital letters. Nobody changed the prompt. The agent simply stopped acting on it.

That is context rot. I spent most of 2026 measuring it, building controls for it and publishing the results. This article explains what I found and how I would handle it in your environment.

What is context rot in an AI agent system?

Context rot is the decay of an agent's governing instructions as the run grows. The rule is still somewhere in the system. The agent no longer behaves as if it applies.

The term became common in 2025 when retrieval researchers showed that model accuracy falls as input length rises, well before the context window is full. In enterprise multi-agent systems the effect is more serious, because the content that decays is policy. An approval threshold, a data residency rule, a "never email the customer without consent" clause.

While writing my paper I collected the published measurements available at the time. They put policy compliance at about 32% after fifty turns, policy violations at about 30% after a single context summary, and unauthorised actions at up to 20% after one handoff between agents. They did not surprise me. Replaying long sessions from real pipelines shows the same shape.

How do you know your enterprise has context rot?

Most teams find it through an incident. You can find it earlier if you look for these signs:

  • The agent passes every test in a short session and fails the same test at turn sixty.
  • A second agent in the pipeline does something the first agent was told never to do.
  • After a "context compaction" or summary step, numeric thresholds change slightly. 10,000 becomes "around ten thousand", then "a high-value amount".
  • A policy update is rolled out, and sessions that were already running keep using the old rule for hours.
  • Your evaluation scores are stable but your audit findings are rising.

If two of these are familiar, the system has rot and the pilot results no longer describe production.

Why do the usual fixes fail?

I have watched teams try the same four fixes. Each one helps for a while.

A bigger context window. More room delays eviction. It also makes the rule a smaller share of what the model attends to. Long windows are where rules get ignored.

Repeating the system prompt. Blind repetition on a timer wastes tokens when the agent is behaving and arrives too late when it is not.

Putting policies in a vector store. Retrieval ranks by similarity to the current task. A rule about refunds is rarely similar to a message about a delivery address, so the rule is not retrieved at the moment it matters.

Asking the agents to pass rules along. Agents paraphrase. After two handoffs a clause has been reworded twice and a condition has gone missing.

The shared mistake is treating a rule as ordinary text. Text in a context window is advice. Enterprises need rules to carry authority.

Where does context rot actually happen?

In the paper I locate it at four points of the agent stack. I call them loci.

Where What goes wrong What it looks like in production
Inside the window The rule is present but attention has moved on Correct at turn 5, wrong at turn 60
Compaction A summary drops or rewrites the clause Thresholds drift, conditions disappear
Memory retrieval Similarity search does not return the rule Agent acts without the clause in view
Handoff The rule is relayed as free text, or not at all Downstream agent breaks an upstream rule

All four end at the same place: a tool call. An agent can think anything. Damage happens when it calls the payment API. That observation shapes the whole design.

How do I engineer context so the rules survive?

The design I published is called the Charter Coherence Protocol, or CCP. It has six parts, and each one answers a failure in the table above.

  1. Keep rules in a charter store. Every clause is a record with an ID, a version, a scope and a signature. The prompt no longer owns the rules.
  2. Give rules a locked segment of the context window. The runtime selects the clauses that apply to the current step and places them where compaction is not allowed to touch them.
  3. Probe, then refresh. The runtime periodically tests whether the agent still follows each clause. When adherence drops it refreshes sooner, and when adherence holds it backs off. I borrowed the control rule from TCP congestion control, because the problem has the same shape: send as little as possible, react fast to loss.
  4. Gate every tool call. Before any action reaches a system of record, a gate checks it against the full live charter. This is the structural guarantee. It does not depend on which model sits behind the agent.
  5. Keep running sessions coherent. When a clause changes, a directory invalidates the old copy in every live session, the way a cache coherence protocol does in hardware.
  6. Hand off clause IDs, not sentences. Agents exchange rule identities through a three-way handshake, and the receiving agent acknowledges the obligations it now holds.

You do not replace your orchestration framework, your memory store or your model. You point the agents at the runtime and add one hook per layer.

What did this achieve, and what does it cost?

I tested CCP in a simulated enterprise multi-agent system with every form of rot injected on purpose. Rule violations executed at tools fell from between 60 and 79% of binding steps to zero in every scenario. Violations the model merely proposed fell to between 6.5 and 14%, and the gate caught those. Paraphrased rules, mutated thresholds and stale actions were removed entirely.

The cost was 1.2 to 1.7 times the baseline token spend. For a workflow that moves money or touches regulated data, I consider that cheap. The full method and results are in my paper in IJARST.

What would I do in your first 30 days?

  • Week 1. List the ten rules that would cause an audit finding if broken. Write each as a testable clause.
  • Week 2. Replay real long sessions and measure adherence per clause at turn 10, 50 and 100, and after every summary and handoff. This gives you a rot profile.
  • Week 3. Put a gate in front of the three highest-risk tools. This alone removes the worst outcomes.
  • Week 4. Move the clauses out of prompts into a versioned store and add probe-based refresh.

This order matters. Enforcement first, because it protects you while the rest is built.

What changes in 2027?

Agent runs are getting longer. In late 2026 most enterprise agents I see run for hours. The roadmaps I am shown plan for runs of weeks, across agents from several vendors that speak A2A and MCP. A rule will then have to survive across companies, and "the prompt said so" will not satisfy a regulator. I expect signed, portable rule sets to become a standard part of agent interoperability. Teams that separate rules from prompts now will be ready for that.

Frequently asked questions

What is context rot?

Context rot is the gradual loss of an AI agent's governing instructions as its run gets longer. The rule still exists in the system, but the agent stops acting on it because of long context windows, summarisation, weak retrieval or handoffs between agents.

Does a larger context window solve context rot?

No. A larger window delays eviction, but it also dilutes attention. Rules are often ignored inside long windows even though they are still present. Protected placement, measured refresh and a gate at the tool call are needed.

What is the difference between context engineering and prompt engineering?

Prompt engineering writes the instruction. Context engineering decides what the model sees at every step of a long run: which rules, which memory, which tool results, in what position and for how long. In production agents, context engineering has more effect on reliability.

Do I need to change my LLM or agent framework to fix context rot?

No. The approach I use runs beside the existing orchestration framework, memory store and model. It adds one hook per layer: a rule store, a protected window segment, a refresh controller and a gate in front of tools.

How do I test whether my agents have context rot?

Replay long sessions and measure adherence to each rule at several depths, for example turn 10, 50 and 100, and again after every summary and every handoff. A drop between depths is your rot profile.
