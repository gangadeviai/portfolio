Long-Running Autonomous Agent Execution

Can Your AI Agent Survive a Five-Day Task? Engineering Long-Running Autonomous Agent Execution

GJ
By Gangadevi JeyarajSenior Agentic AI Engineer · CPO, Enthiram.ai · 15 years in AI
20 November 2026 · 7 min read

The short answer

A long-running agent needs its progress stored outside the model and outside the process. I run the agent as a durable workflow: every step is recorded, any failure resumes from the last completed step, actions are idempotent so retries are safe, and waits for people or other systems cost nothing. The context window is rebuilt for each step from that stored state.

Key takeaways

  • An agent that keeps its state in memory or in the chat history will lose work the first time something restarts.
  • Durable execution turns a crash into a pause. The run continues from the last completed step.
  • Every tool call that changes something needs an idempotency key, or a retry will pay twice.
  • Set budgets for steps, tokens and elapsed time, and decide in advance when the agent must hand over to a person.

A demo agent finishes in ninety seconds. A real insurance claim exception takes days. The agent asks the customer for a missing document and waits. It asks an adjuster to approve a payout and waits again. In between, the service is redeployed twice, a model endpoint has a bad hour, and a rate limit is hit.

I built the claims-exception agent at Enthiram.ai for exactly this kind of work. It brought each case from about 14 days to about 3.5 hours of handling time. Most of the engineering effort did not go into prompts. It went into making sure the agent could be interrupted at any moment and carry on correctly.

Why do agents fail on long tasks?

The causes are ordinary, which is why they are overlooked in pilots.

What happens Agent with in-memory state Result
The process restarts during a deploy State is gone Case starts again or is abandoned
A tool call times out Agent retries blindly Duplicate payment or duplicate email
A human takes two days to approve Session expires Approval arrives to nothing
The model API fails mid-run Exception Half-finished case, unknown status
The conversation grows for days Context fills with old tool output Rules and goals get lost
The agent loops on a hard case No limit A large bill and no outcome

None of these is an AI problem. They are distributed systems problems that agents inherit the moment a task outlives one request.

What is durable execution, and why do I use it?

Durable execution means the engine running your workflow saves every step and its result as it happens. If the process dies, another worker loads that history and continues from the next step. To the code, the crash never occurred.

I use Temporal for this. The split is simple and it matters:

  • The workflow is the long-lived logic of the case. It holds the plan, the state and the waits. It contains no direct calls to the outside world.
  • Activities are the individual actions: call the model, query the policy system, send an email, request a payment. Each one has a timeout and a retry policy.

A LangGraph agent does the reasoning inside an activity. Temporal owns the lifetime of the case. The agent stays flexible and the process around it stays predictable.

How do you make retries safe?

Networks fail after the work has been done and before the confirmation arrives. The engine cannot tell the difference, so it retries. If the action was "pay the claimant", you have paid twice.

The fix is an idempotency key on every call that changes something. I derive it from the case ID and the step number. The payment service sees the same key a second time and returns the original result without acting again. Where a downstream system cannot honour a key, I check its state first and act only if the change is missing.

For multi-step changes I define a compensation for each step, following the saga pattern. If step four fails for good, the workflow reverses steps three, two and one in order: release the reserve, cancel the notification, reopen the task.

How does an agent wait for days without wasting resources?

In a durable workflow, waiting is a stored timer or a signal. No process sits idle and no session stays open.

When the claims agent needs an adjuster's approval, the workflow records "waiting for approval on case 4471, escalate after 24 hours" and stops. When the adjuster clicks approve, a signal wakes the workflow at that line. If nobody responds, the timer fires and the case goes to a supervisor. The same pattern handles a customer who uploads a document three days later.

This is also where human oversight sits. I decide per action, in advance, which ones the agent may take alone and which ones need a signature. High-value payouts and anything irreversible wait for a person.

What goes into the context window on day four?

Not the whole history. A transcript of four days of tool calls would bury the goal and the rules under old output.

I treat the workflow state as the source of truth and rebuild the context for each step from it: the goal, the applicable rules, a short summary of what has been done, the open items, and the fresh data for this step. Old tool output stays in the history where it can be audited, and out of the prompt.

This design is what led me to study rule decay in long runs in detail. I wrote that up in context rot and context engineering.

Which limits should every long-running agent have?

An autonomous agent without budgets is an open commitment. I set these on every workflow.

  • Step budget. A maximum number of plan and act cycles per case.
  • Token and cost budget. A ceiling per case, with a warning at 70%.
  • Time budget. A deadline for the whole case and for each wait.
  • Repeat detection. The same tool called with the same arguments three times means the agent is stuck.
  • A kill switch. Operations can pause one case, one workflow type or everything, and resume later without loss.

When a budget is reached the agent does not fail. It packages what it knows and hands the case to a person with a clear summary.

How do you change the agent while cases are in flight?

On any given day, hundreds of cases are part-way through. A new prompt, a new tool or a new model version must not corrupt them.

I version workflows so that running cases finish on the logic they started with and new cases take the new version. Model upgrades go to a small share of new cases first, with evaluation on the results before the rest follow. I describe that gate in agent observability and continuous evaluation.

What would I do in your first 30 days?

  • Week 1. Choose one process that takes days and has clear waits. Draw its steps and mark which ones change external systems.
  • Week 2. Implement it as a durable workflow with the agent in activities. Add idempotency keys to every write.
  • Week 3. Add approvals as signals, escalation timers and budgets.
  • Week 4. Test failure on purpose: stop workers mid-case, fail the model endpoint, replay duplicates. Go live only when every test resumes cleanly.

What changes in 2027?

Runs are stretching from days to weeks, and they are crossing company boundaries as agents hand work to suppliers' and partners' agents. Durable state will have to be shared across organisations, with agreement on who owns a task at each moment. Model versions will also change during a single run more often, so pinning and replay will become routine. The teams that already treat an agent run as a durable, versioned process will find this a small step.

Frequently asked questions

What is a long-running AI agent?

It is an agent that works on a task for hours, days or weeks, across restarts, waits for people and other systems, and many tool calls. Examples include claim handling, procurement and compliance reviews.

What is durable execution for AI agents?

Durable execution records every step of a workflow and its result. If a process crashes or is redeployed, the run resumes from the last completed step. Engines such as Temporal provide this.

How do you stop an agent from repeating an action after a retry?

Attach an idempotency key to every call that changes something, so the receiving system ignores repeats. Where that is not possible, check the current state first and act only if the change has not happened.

How do long-running agents handle human approval?

The workflow stores a wait and stops. An approval arrives as a signal and the workflow continues from that point. A timer escalates the request if nobody responds in time.

Should I use LangGraph or Temporal for long-running agents?

They solve different problems and work well together. LangGraph structures the agent's reasoning and tool use. Temporal provides durable execution, timers, retries and versioning for the process around it.
