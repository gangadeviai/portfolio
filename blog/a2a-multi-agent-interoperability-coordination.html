A2A, Multi-Agent Interoperability & Coordination

Your AI Agents Come from Five Vendors and Cannot Work Together: A2A, MCP and Multi-Agent Coordination

GJ
By Gangadevi JeyarajSenior Agentic AI Engineer · CPO, Enthiram.ai · 15 years in AI
23 November 2026 · 7 min read

The short answer

Use MCP to connect agents to tools and data, and A2A to connect agents to each other. Then add what the protocols leave to you: typed task contracts, one owner per task, shared identity, budgets, tracing across agents, and a handoff that transfers obligations along with the work. Interoperability gets agents talking. Coordination gets the job finished.

Key takeaways

  • MCP and A2A are complementary. One reaches tools, the other reaches agents.
  • Most multi-agent failures happen at handoff: lost context, lost rules, or two agents each assuming the other owns the task.
  • Give every task a typed contract, a single owner, a deadline and a budget.
  • Pass rule identities at handoff, and have the receiving agent acknowledge them.

By late 2026 the question I hear from architects has changed. A year ago it was "which agent framework should we standardise on?" Now it is "we have agents inside our CRM, our service desk, our ERP and three that we built ourselves. How do we make them work as one?"

No enterprise will run on a single framework. Software vendors ship their own agents, and business units build more. The practical task is to make a mixed population of agents cooperate safely.

What do MCP and A2A each do?

They solve different problems and I use both.

Protocol Connects Think of it as Use it for
MCP (Model Context Protocol) An agent to tools and data A standard port for capabilities Querying a database, calling an API, reading documents
A2A (Agent2Agent) An agent to another agent A standard way to delegate work Handing a task to a specialist agent and tracking it

With MCP, an agent calls a function and gets a result. The other side is a tool with no goals of its own.

With A2A, an agent asks another agent to achieve something. The other side plans, may take a long time, may come back with a question, and reports progress. Each agent publishes an agent card that describes its skills, its endpoint and how to authenticate. Work is exchanged as tasks that move through states such as submitted, working, input required and completed.

Both are open standards under neutral foundations, which is why I am comfortable building on them. Neither tells you how to run a team of agents well.

Why do multi-agent systems fail even when the agents can talk?

Connecting agents is the easy half. I group the failures I see into five.

  • Lost in handoff. Agent A summarises the case in a paragraph. A constraint is left out. Agent B acts without it.
  • Nobody owns it. Two agents each believe the other is handling the customer reply. Or both send one.
  • Loops. A asks B, B asks C, C asks A. Tokens are spent and nothing completes.
  • No shared identity. The downstream agent cannot tell on whose behalf it is acting, so it either refuses everything or permits everything.
  • Invisible cost. Agents chat freely. A simple request generates forty model calls across five systems, and no single team sees the bill.

These are coordination failures. A protocol gives you a common language. You still have to decide who does what.

Which coordination pattern should you choose?

I choose by how predictable the work is.

Pattern How it works Fits
Orchestrator and workers One coordinator splits the job and assigns specialists Most enterprise processes with a clear owner
Pipeline Each agent hands to the next in a fixed order Stable, staged work such as document intake
Event-driven Agents react to events on a shared stream Loosely coupled teams, monitoring, high volume
Peer negotiation Agents request and offer work to each other Cross-company scenarios, still immature

For the insurance claims system I designed, I used an orchestrator with three specialists: a claims agent that assembled the case, an assessor agent that applied policy terms, and a fraud agent that scored risk. A person approved high-value outcomes. I chose this pattern because accountability was clear. At any moment one component owned the case.

My general advice is to start with an orchestrator. Free-form conversation among agents is interesting in a lab. In an enterprise it is hard to audit and hard to cap.

What should a task contract contain?

Every delegation between agents is a contract. I make it explicit and typed.

  1. Goal and inputs in a schema, with IDs that refer to records in the knowledge layer. A paragraph of prose is not an input.
  2. Expected output in a schema, so the caller can validate it.
  3. Owner. Exactly one agent owns the task at a time. Ownership moves only on acknowledgement.
  4. Deadline and budget. A time limit, a step limit and a cost limit. On breach, the task returns to the coordinator.
  5. Obligations. The rules that travel with the work.
  6. Trace ID. The same identifier across every agent and tool call.

The fifth item deserves more explanation, because it is where my own research went.

How do rules survive a handoff?

When agents relay rules to each other in natural language, the rules degrade. A threshold is rounded. A condition is dropped. After two hops the downstream agent is following something the business never wrote.

In the Charter Coherence Protocol I published this year, the handoff carries clause identities, not text. It works as a three-way handshake:

  1. The sending agent offers the task with the IDs of the rules that apply.
  2. The receiving agent loads those clauses from the authoritative store and acknowledges them.
  3. The sender confirms, and responsibility for those obligations transfers.

Because the receiver reads each rule from the source, nothing is paraphrased. Because it acknowledges, there is a record of who was responsible at each moment. I explain the wider design in context rot and context engineering.

How do identity and security work across agents?

Three identities are present in every call, and all three need to be verified.

  • The agent. Is this really the payments agent, and is it permitted to request this?
  • The user. On whose behalf is the chain acting? Their entitlements limit what any agent in the chain may do.
  • The task. Is this request part of an approved task, within its budget?

In my own systems the MCP servers were secured with OAuth2 and OIDC, and the user's identity was carried through. A2A supports the same standards. The principle I hold to is that delegation never increases privilege. An agent cannot gain access by asking another agent to do something it could not do itself.

Content from another agent is also treated as data, not as instruction. An external agent's message may contain text that tries to redirect yours. The tool gate checks actions against policy regardless of who suggested them.

What would I do in your first 30 days?

  • Week 1. Inventory every agent in the enterprise, bought or built: what it can do, what it can access, who owns it.
  • Week 2. Pick one process that crosses two agents. Define the task contract and the single-owner rule.
  • Week 3. Connect them over A2A with a coordinator, shared trace IDs and budgets.
  • Week 4. Test handoffs under failure: slow replies, refusals, conflicting outputs. Add obligation handoff for the three most important rules.

What changes in 2027?

Agents will increasingly deal with agents outside the company: a supplier's, a bank's, a customer's. That raises questions that technology alone does not answer. Who is liable when a partner's agent acts on a task yours delegated? How do you trust an agent card? I expect signed agent identities, shared registries and contract terms written for agent-to-agent work to become ordinary parts of procurement. The engineering groundwork is the same as above: explicit contracts, verified identity and obligations that travel with the task. For keeping all of it visible, see agent observability and continuous evaluation.

Frequently asked questions

What is the A2A protocol?

A2A, or Agent2Agent, is an open protocol that lets AI agents built on different frameworks discover each other, delegate tasks and track their progress. Agents describe themselves with agent cards and exchange work as tasks with defined states.

What is the difference between MCP and A2A?

MCP connects an agent to tools and data sources. A2A connects an agent to other agents. An enterprise system normally uses both: A2A for delegation between agents and MCP for each agent's access to tools.

Why do multi-agent systems fail in production?

The most common causes are context and rules lost at handoff, unclear task ownership, loops between agents, missing shared identity and uncontrolled cost. These are coordination problems that protocols alone do not solve.

Which multi-agent coordination pattern is best for enterprises?

An orchestrator with specialist worker agents suits most enterprise processes because ownership and audit are clear. Pipelines fit fixed staged work, and event-driven designs fit loosely coupled, high-volume scenarios.

How do you keep policy rules intact when agents hand off work?

Pass the identities of the applicable rules with the task, have the receiving agent load them from the authoritative store and acknowledge them, and record the transfer. Rules relayed as free text are paraphrased and degrade.
